## Issues by severity

### [P0] No `<h1>` on the homepage, blog index, or tags index — and heading order is broken

**Location**: `src/pages/index.astro:16,17,70` · `src/pages/blog/[...page].astro` · `src/pages/tags/index.astro`

The homepage opens with `<h3>Hey 👋 I'm tncrd</h3>`, follows with `<h4>`, then later `<h2>Latest posts</h2>`.
There is no `<h1>` anywhere on the page. The blog listing and tags index contain **no headings at all** —
their page titles are rendered as plain text.

**Impact**: WCAG 2.1 **1.3.1 Info and Relationships (Level A)** violation. Screen-reader users navigating by
heading (the primary navigation mode for most SR users) get no document title and land in a structure that
descends to h4 before ascending to h2. It also costs you SEO — three of your main pages have no `<h1>`.

**Fix**:
- `index.astro:16` — `<h3 class="text-3xl …">` → `<h1 class="text-3xl …">`
- `index.astro:17` — `<h4 class="text-1xl …">` → `<p class="text-lg …">` (it is a tagline, not a section)
- Add a visible `<h1>` to `pages/blog/[...page].astro` and `pages/tags/index.astro`, or an `sr-only` one
  if the breadcrumb is meant to carry the visual weight.

### [P1] The `--accent` token is semantically miswired — hover and focus states fail contrast

**Location**: `src/styles/global.css:70,84` (definitions) · consumed at `ui/button.tsx:16,20`,
`ui/badge.tsx:19`, `ui/dropdown-menu.tsx:75,93,129,212`

This is the single highest-leverage finding.

In stock shadcn, `--accent` is a **near-neutral hover surface**, not a brand color. Your theme redefines it
to a saturated blue-violet while leaving `--accent-foreground` at its original near-black / near-white value:

```css
/* light */ --accent: oklch(54.67% 0.2475 275.21);  --accent-foreground: oklch(0.205 0 0);
/* dark  */ --accent: oklch(73.85% 0.0976 284.42);  --accent-foreground: oklch(0.985 0 0);
```

Measured contrast of the pair as actually rendered:

| Context | Ratio | WCAG AA (4.5:1 needed) |
|---|---|---|
| Light — ghost/outline button hover, dropdown item focus | **3.31 : 1** | ✗ FAIL |
| Dark — ghost/outline button hover, dropdown item focus | **2.27 : 1** | ✗ FAIL (near-invisible) |

**Impact**: Every ghost-button hover ("See all posts" on the homepage), every outline-button hover (the 404
CTA, all four social icons in the footer), and **every keyboard-focused item in the mobile menu** paints
low-contrast text on a saturated field. In dark mode the mobile menu focus state is white-on-lavender at
2.27:1 — a keyboard user genuinely cannot see where focus is. That is the accessibility floor for the
entire mobile navigation.

The deeper problem: you defined a brand accent that is **never used as a brand accent**. Links are
`foreground`-colored, nav is `foreground/60`, badges are `secondary`. The accent only leaks out through
hover surfaces it was never meant to paint.

**Fix** — separate the two concerns:
```css
:root {
  --accent: oklch(0.97 0 0);           /* restore neutral hover surface */
  --accent-foreground: oklch(0.205 0 0);
  --brand: oklch(54.67% 0.2475 275.21); /* your blue-violet, now addressable */
  --brand-foreground: oklch(0.985 0 0);
}
[data-theme='dark'] {
  --accent: oklch(0.269 0 0);
  --accent-foreground: oklch(0.985 0 0);
  --brand: oklch(73.85% 0.0976 284.42);
  --brand-foreground: oklch(0.205 0 0);
}
```
Register `--color-brand` in the `@theme inline` block, then spend the brand deliberately: link underlines
on hover, the TOC progress ring, the active TOC item, the focus ring. One accent used in three consistent
places reads as a design system; an accent that only appears on hover reads as an accident.

### [P1] Navigation links fail contrast in dark mode

**Location**: `src/components/Header.astro:25` — `text-foreground/60`

`foreground/60` on the dark background measures **3.04 : 1**. AA requires 4.5:1 for text this size (14px).
Light mode is fine at 6.34:1.

**Impact**: Your primary navigation is the hardest-to-read text on the page for dark-mode users —
below AA, and below the level at which the nav reads as interactive at all.

**Fix**: Use `text-muted-foreground` (7.63:1 dark, 4.73:1 light — both pass) and keep
`hover:text-foreground`. This also removes a one-off opacity value in favor of an existing token.

### [P1] `prefers-reduced-motion` is not handled anywhere

**Location**: entire codebase — `grep` for `reduced-motion|motion-reduce|motion-safe` returns zero matches

Animated without an opt-out: BlogCard image grayscale→color (300ms), card background fades, callout
chevron rotations, theme-toggle sun/moon rotate+scale, arrow translate on the homepage and 404 CTAs,
the TOC progress ring, and Astro's view transitions on every navigation.

**Impact**: Users with vestibular disorders have a documented OS-level preference that this site ignores
completely. View transitions on every page navigation are the most likely to cause discomfort.

**Fix**: Add to `src/styles/global.css`:
```css
@media (prefers-reduced-motion: reduce) {
  *, ::before, ::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
  ::view-transition-group(*), ::view-transition-old(*), ::view-transition-new(*) {
    animation: none !important;
  }
}
```
Keep the *state changes* (grayscale still lifts, chevron still points down) — only remove the tweening.
That is the meaningful fallback, not simply disabling the effect.

### [P2] Sticky-header height is a magic number written four different ways

**Location**: `typography.css:39` (`scroll-mt-32` / `xl:scroll-mt-20`) ·
`pages/blog/[...id].astro:126` (`scroll-mt-31`) · `components/TOCHeader.astro` script (`HEADER_OFFSET = 102 + 36`)

Four values — 128px, 80px, 124px, 138px — all trying to describe the same sticky header. `scroll-mt-31`
is a hand-tuned magic number that exists nowhere else in the scale.

**Impact**: Anchor links land inconsistently. Clicking a TOC entry scrolls to a different offset than
following a heading permalink, and both differ from where the scroll-spy thinks the heading is — which is
why the active-section highlight drifts on long posts.

**Fix**: Define the header height once as a CSS custom property and derive everything from it:
```css
:root { --header-h: 3.5rem; --sticky-offset: calc(var(--header-h) + 2rem); }
```
Then `scroll-margin-top: var(--sticky-offset)` in the prose layer, and read it in TS with
`getComputedStyle(document.documentElement).getPropertyValue('--sticky-offset')` instead of `102 + 36`.

### [P2] Prose measure is ~90ch — well past the readable limit

**Location**: `pages/blog/[...id].astro:78` — grid column is `min(calc(var(--breakpoint-md) - 2rem), 100%)`
= 736px, with `article class="prose max-w-none"`

At 16px Geist, 736px is roughly **90 characters** per line. The comfortable range is 60–75ch.

**Impact**: Long-form technical posts with dense math are exactly the content where over-long measure
hurts most — the eye loses its place on the return sweep. This is the highest-impact *readability* fix
on a blog whose whole purpose is long-form reading.

**Fix**: Replace `max-w-none` with `max-w-[68ch]` on the `<article>`, or narrow the grid column to
`min(42rem, 100%)`. Keep full-bleed behavior for code blocks, figures and `.katex-display` by letting
those break out — they already use `mx-auto` and their own overflow containers.

### [P2] Touch targets are 32px in the mobile header

**Location**: `components/ThemeToggle.astro:10` (`size-8`) · `ui/mobile-menu.tsx:39` (`size-8`) ·
`components/SocialIcons.astro:20` (`size: 'icon'` = 36px)

WCAG 2.2 **2.5.8 Target Size (Minimum)** requires 24×24 (met), but the practical guideline and Apple/Google
guidance is 44×44. The theme toggle and hamburger sit **adjacent** in the mobile header at 32px each — the
combination of small and neighboring is what produces mis-taps.

**Fix**: Keep the 32px visual size, expand the hit area:
```
size-8 relative after:absolute after:-inset-1.5 after:content-['']
```
This gets you 44px of tappable area without changing the layout.

### [P2] Gray text on tinted callout backgrounds, and a 25-variant palette with collisions

**Location**: `components/Callout.astro:6-115`

Two problems in one component:

1. **Gray on color** — `proof`, `remark`, `notation`, `proposition` use `text-gray-700` / `text-slate-700`
   on a tinted background. Neutral gray on a colored field reads as dirty; the tint should come from the
   same hue family as the border.
2. **Semantic collisions** — 25 variants sharing colors: `theorem` and `answer` are both `teal-500`;
   `important` and `definition` are both `purple-500`; `example` and `solution` are both emerald;
   `proof` and `remark` are both gray; `explanation` and `conjecture` both use `lucide:help-circle`.

**Impact**: The color stops carrying meaning. If a reader sees teal and cannot tell whether it is a theorem
or an answer, the entire color system is decorative rather than informational — and it reads as a rainbow.

**Fix**: Collapse to 6–8 semantic families and distinguish within a family by icon, not hue:
- **Structural** (definition, notation) — one hue
- **Assertive** (theorem, lemma, proposition, corollary, axiom) — one hue
- **Derivational** (proof, solution, answer) — one hue
- **Pedagogical** (intuition, explanation, example, recall, remark) — one hue
- **Interrogative** (exercise, problem, conjecture) — one hue
- **Advisory** (note, tip, warning, danger, important, summary) — existing semantic colors

Replace every `text-gray-*` / `text-slate-*` with the family's own hue at a darker step.

### [P2] Emoji served as `<img>` from an external CDN, with incorrect alt text

**Location**: `pages/index.astro:38-42,51-55`

```html
<img src="https://images.emojiterra.com/mozilla/512px/1f4bb.png" alt="AI robot" …>
```

Three problems: the laptop emoji (`1f4bb`) is labeled **"AI robot"**; both images are decorative and should
be `alt=""`; and a site that carefully self-hosts its variable fonts makes two blocking third-party requests
for 512px PNGs rendered at 16px.

**Impact**: Wrong alt text is worse than none — a screen reader announces "AI robot" next to the words
"Computer Science". Also a privacy leak (emojiterra and jsdelivr see every homepage visitor) and a
render-blocking dependency on a CDN you do not control.

**Fix**: Use the Lucide icons already installed (`lucide:laptop`, `lucide:brain-circuit`, `lucide:code`)
via the `Icon` component, or inline the emoji as text characters. Set `alt=""` if any image remains.
The Python logo at `index.astro:73` has the same CDN issue but its alt text is correct.

### [P3] `text-1xl` is not a real class

**Location**: `pages/index.astro:17`

There is no `text-1xl` in Tailwind — the element silently renders at the inherited base size. Whatever
size was intended never applied. (Fixed together with the `<h1>` change above.)

### [P3] Scroll handlers are unthrottled

**Location**: `components/TOCHeader.astro` — `window.addEventListener('scroll', …)`

`handleScroll` runs `getVisibleIds()` on every scroll event, which reads `offsetTop`/`offsetHeight` for
every heading — forcing layout on each fire. On a long post like the extreme-value-theory piece this is
dozens of forced reflows per second.

**Fix**: Wrap in a `requestAnimationFrame` guard, or replace the whole scroll-spy with an
`IntersectionObserver`, which is the purpose-built API and eliminates the layout reads entirely.

---

### [P3] `transition-all` on every button

**Location**: `ui/button.tsx:8`

`transition-all` animates every animatable property including layout-affecting ones. Stock shadcn ships
this; it is not your code, but it is worth narrowing to
`transition-[color,background-color,border-color,box-shadow]`.

---

### [P3] BentoBox can squash images on mobile

**Location**: `components/BentoBox.astro:24` — `grid-cols-1 sm:grid-cols-4 … aspect-square`

Below `sm`, N images stack into one column inside a container forced to `aspect-square`. Each image gets
1/N of a square with `object-cover` — heavily cropped. The `row-span-*` classes also have no effect at
one column.

**Fix**: Drop `aspect-square` below `sm`, or switch to `aspect-auto grid-cols-2` on mobile so the span
classes still mean something. (Low priority — the component is not currently used in published posts.)

## What's working

Preserve these. They are the reason the site reads as considered rather than generic, and several fixes
above could accidentally break them.

- **Self-hosted Geist variable font** with `font-display: swap` and a full 100–900 axis. A real
  typographic decision, not a system-font default — this alone puts the site ahead of most personal blogs.
- **OKLCH token set throughout.** Perceptually uniform, so opacity modifiers like `foreground/80` behave
  predictably. The right foundation; it just needs the `accent` wiring corrected.
- **The restrained monochrome palette.** Near-zero chroma for all surfaces and text, with color reserved
  for semantic callouts, is a genuinely confident editorial choice and the opposite of AI-default styling.
- **The `:where()`-based prose layer** with `not-prose` escape hatches — zero specificity, fully
  overridable, and the `small` / `fix-margin` utilities are a clean way to handle nested-context density.
- **Grayscale→color on BlogCard hover.** Restrained, meaningful, uses a compositable property, and gives
  the listing a distinct personality. Keep it (just gate it on reduced-motion).
- **Overflow discipline in prose** — tables, `<pre>`, and `.katex-display` each get their own
  `overflow-x-auto`. No horizontal page scroll anywhere, which is exactly right for math-heavy content.
- **The theme toggle's transition-suppression trick** — adding `[&_*]:transition-none`, forcing a reflow,
  then removing it on the next frame. Prevents every element on the page from cross-fading during a theme
  switch. Genuinely sophisticated.
- **Semantic landmarks** — `header` / `nav` / `main` / `article` / `footer`, `role="list"` on the social
  list, `sr-only` labels and `aria-label` on icon-only controls.
- **Spacing discipline.** Consistent use of the Tailwind scale (`gap-y-6`, `gap-4`, `p-4`, `p-6`) with
  almost no arbitrary values — the nine `[3px]` underline offsets are intentional and consistent.

## Recommended next steps

Ordered by impact per unit of effort. Steps 1–4 are roughly 45 minutes total and move the score to ~16.

1. **Fix the `--accent` / `--brand` split** (`global.css`). One edit, repairs every hover and focus state
   site-wide, and unlocks a brand color you can actually use. Highest leverage in the audit.
2. **Fix the heading hierarchy** — add `<h1>` to the homepage, blog index and tags index; correct the
   h3→h4→h2 order on the homepage. Clears the P0.
3. **Add the `prefers-reduced-motion` block** to `global.css`. Ten lines, covers the whole site.
4. **Two one-line fixes**: nav `text-foreground/60` → `text-muted-foreground`; `hover:bg-gray-100` →
   `hover:bg-secondary` (×2).
5. **Constrain the prose measure** to ~68ch. The biggest readability win for long-form posts.
6. **Replace the CDN emoji images** with Lucide icons and fix the alt text.
7. **Tokenize the header height** and derive all four scroll offsets from it.
8. **Restructure the callout palette** into 6–8 semantic families. Largest effort; do it when you next
   touch a math-heavy post so you can verify the semantics against real content.
9. Expand the mobile touch targets, then pick off the P3s.

Re-run `design-audit` after fixes to see your score improve.
